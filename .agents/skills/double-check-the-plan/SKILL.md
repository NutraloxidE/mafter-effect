# /double-check-the-plan — プラン二重チェック

実装に入る**前**に、プランの不明瞭さを **2 回の独立したレビュー**で洗い出す。
本スキルは**レビュー専用** — コード変更・spec 編集・実装は行わない（指摘とプラン修正案の提示まで）。

> **目的**: 「実装者が明日から手を動かせるか？」を Pass 1（網羅）と Pass 2（反証）で検証する。
> 実装フェーズは [implementation-loop](../implementation-loop/SKILL.md)。深い設計判断は [delegate-to-thinking-model](../delegate-to-thinking-model/SKILL.md)。

## いつ使うか

| 向いている | 向いていない |
|-----------|-------------|
| `.cursor/plans/*.plan.md` 確定前の最終レビュー | すでに実装中・差分レビュー |
| Plan Mode 出力の品質ゲート | 単発の技術質問 |
| 委任前（delegate-to-cursor / orchestrate）の手渡し確認 | バグのピンポイント修正 |
| 大きな機能のフェーズ分割後 | 1 行の変更計画 |

**併用**: 指摘を反映したプラン修正後、必要ならもう一度本スキルを回す。実装開始は Pass 2 で **ブロッカー 0 件**（またはユーザー承認済み）を推奨。

## コマンド構文

| 入力 | 動作 |
|------|------|
| `/double-check-the-plan` | 会話内の直近プラン、または `.cursor/plans/` の対象を特定して二重チェック |
| `/double-check-the-plan <path>` | 指定ファイル（例 `.cursor/plans/foo.plan.md`）を対象に二重チェック |
| `/double-check-the-plan`（Plan Mode 直後） | そのセッションで確定したプランを対象 |

対象が複数ある・不明なときは **1 つに絞るようユーザーに確認**（推測で古いプランをレビューしない）。

## 事前読み込み（両 Pass 共通）

レビュー開始前に、対象プランのスコープに応じて読む:

1. 対象プラン全文
2. [progress.md](../../../progress.md) — 前提・既知バグ・Next steps との整合
3. [doc/mafter-effect-spec.md](../../../doc/mafter-effect-spec.md) の該当節（§5 型 > §4 INV > §15 受け入れ）
4. プランが参照する既存 verify・スパイク報告・ハンドオフ（`RG-*`）があれば該当箇所のみ

**読まずに推測で指摘しない。** プランと spec が矛盾する場合は指摘に昇格する。

---

## Pass 1 — 網羅スキャン（不明瞭・抜け）

プランを**上から順に**読み、次の観点で **Issue** を列挙する。
各 Issue には ID（`P1-1`, `P1-2`, …）、重大度、該当箇所（見出し・行・節名）、説明、**実装者が取るべきアクション**（質問 / 決定 / 追記）を付ける。

### 重大度

| ラベル | 意味 |
|--------|------|
| 🔴 **ブロッカー** | このままでは着手不可、または誤実装が確実 |
| 🟡 **要澄清** | 着手はできるが途中で止まる・手戻りが大きい |
| 🟢 **改善** | 明確だが、追記すると実装が楽 |

### Pass 1 チェックリスト

**スコープ・完了条件**

- [ ] 一行結論（何を・何をしない）があるか
- [ ] 受け入れ条件が**測定可能**か（verify 名・数値ゲート・exit 0 等）
- [ ] 「後で」「様子見」「必要なら」に**ゲートまたは期限**が無いか
- [ ] スコープ外が明示されているか（触らないファイル・経路・型）

**決定・前提**

- [ ] 設計分岐（A/B/C…）で**推奨が 1 つに固定**されているか、未決なら誰が決めるか
- [ ] 暗黙の前提（既存挙動・データ形状・性能上限）が書かれているか
- [ ] §5 型 / INV / `project.json` 直列化に触れる記述と、**ユーザー確認要否**が一致しているか

**実装可能性（Mafter Effect 固有）**

- [ ] [implementation-loop](../implementation-loop/SKILL.md) Phase 2 相当の**影響経路**が列挙されているか（preview / export / bundle / resolve / store / タイムライン）
- [ ] 新型・`c.type` 分岐なら [add-layer-component-type](../add-layer-component-type/SKILL.md) の配線観点がプランにあるか
- [ ] レンダリング変更なら **INV-2**（経路間 parity）の検証方針があるか
- [ ] `src/runtime` / expression 変更なら **`npm run build:player`** が計画に含まれるか
- [ ] export 共有パイプライン変更なら**既存 verify 無回帰**が完了条件に含まれるか

**依存・順序・リスク**

- [ ] フェーズ間の依存が循環していないか
- [ ] スパイク・0b ゲートの**不合格時のピボット**が書いてあるか
- [ ] ファイル単位のタスクに**完了の定義**があるか（「実装する」だけで終わっていないか）

**検証・記録**

- [ ] 各フェーズに対応する test / `verify-*.mjs` / 手動確認が割り当てられているか
- [ ] `progress.md` 追記タイミングが書いてあるか（任意だが推奨）

**言語・曖昧表現**

次の語が**定義なし**で使われていないか grep する:  
`適切に` `必要に応じて` `基本的に` `など` `検討` `改善` `対応` `整える` `最適化` `互換`

Pass 1 の出力は **Issue 一覧のみ**（まだ総合判定しない）。

## Pass 2 — 反証再読（もう一度、別の眼で）

**Pass 1 の Issue 一覧は一旦脇に置き**、プラン全文を**最初から再読**する。
Pass 2 では次を行う（Pass 1 の言い換え禁止）。

### Pass 2 の 4 つの問い

1. **反証**: 「このプランの推奨経路が**間違っている**としたら、何が書かれていないか？」
2. **実装者**: 「明日の自分がこのプランだけ持って着手したら、**最初の 30 分で何を質問するか？**」（質問を列挙）
3. **完了判定**: 「各フェーズの Done は、第三者が**コマンド 1 つ**で Yes/No 判定できるか？」
4. **隠れスコープ**: 「プランに無いのに、実装で**必ず触る**共有コードは何か？」（`rasterCapture` / `DomRenderer` / `resolve` / store 等）

### Pass 2 追加ルール

- 新たな Issue は ID `P2-1`, `P2-2`, … で付与（Pass 1 と別系列）
- Pass 1 で拾えなかった項目を**必ず 1 件以上**探す努力をする（無ければ「Pass 2 独自の新規 Issue なし」と明記し、その理由を 1 文で書く）
- Pass 1 と**同じ内容**の指摘は「重複」として 1 行でマージし、重大度は高い方を採用

## 統合レポート（最終出力）

Pass 1・Pass 2 完了後、チャットに次の形式で**1 回だけ**報告する。

```markdown
# プラン二重チェック: <プラン名またはファイル>

## 総合判定
- [ ] 実装着手可
- [ ] 要修正（ブロッカー <N> 件）
- [ ] 要再設計（根本的分岐が未決）

## ブロッカー（着手前に解消）
| ID | 箇所 | 問題 | 推奨アクション |
|----|------|------|----------------|
| … | … | … | … |

## 要澄清
| ID | 箇所 | 問題 | 推奨アクション |
| … |

## 改善（任意）
- …

## Pass 2 独自の気づき（要約 1–3 文）
…

## プランへの追記案（任意・diff 風）
箇条書きで、コピペ可能な追記文案のみ。長文の書き換えはしない。

## 次の一手
1. …
2. …
```

### 総合判定の基準

| 判定 | 条件 |
|------|------|
| **実装着手可** | ブロッカー 0。要澄清は実装者がプラン内の既定で進められる、またはユーザーが既に口頭承認済み |
| **要修正** | ブロッカー 1 件以上、または要澄清が 3 件超で着手直後の停止が確実 |
| **要再設計** | 推奨経路が未固定、§5/INV 変更が必要だがプランに載っていない、ゲート数値が欠落 |

---

## やってはいけないこと

| アンチパターン | 理由 |
|----------------|------|
| Pass 2 を Pass 1 の要約だけで済ませる | 二重チェックの意味がない |
| 指摘しながら実装・spec 編集を始める | 本スキルはレビュー専用 |
| ブロッカーを「実装しながら決めよう」で残す | implementation-loop Phase 1 違反 |
| 古いプランを推測でレビュー | 誤った前提で時間を浪費 |
| 総合判定を Issue 列挙前に出す | 順序の強制 |

## ワークフロー例

```
Plan Mode で .cursor/plans/feature-x.plan.md を作成
    ↓
/double-check-the-plan .cursor/plans/feature-x.plan.md
    ↓
Pass 1 網羅 → Pass 2 反証 → 統合レポート
    ↓
要修正ならプラン著者が追記（ユーザーまたは Agent の plan 編集）
    ↓
ブロッカー 0 になったら implementation-loop Phase 0 へ
```

委任する場合: 本スキルで **ブロッカー 0** を確認してから [delegate-to-cursor](../delegate-to-cursor/SKILL.md) / [orchestrate-cursor-agents](../orchestrate-cursor-agents/SKILL.md) に渡す。
